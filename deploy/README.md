# Развёртывание NailsProfi на VPS Beget

Эта папка хранит пример будущей настройки VPS. Сейчас она ничего не
публикует и не меняет на Beget.

Сайт собран на Astro и после `bun run check` полностью находится в
`website/dist/`. Codex остаётся на Mac: он собирает сайт локально и загружает
готовые файлы на VPS по SSH. На сервере не нужны Codex, Bun, Node.js, Git,
Docker, база данных или постоянно работающий процесс приложения.

## Схема

```text
Mac с Codex
  -> bun run check
  -> website/dist/
  -> SSH + rsync
VPS Beget
  -> /var/www/nailsprofi/releases/<дата>-<commit>
  -> /var/www/nailsprofi/current
  -> Nginx
  -> домен и HTTPS
```

Новая версия сначала полностью загружается в отдельный каталог. Только после
этого ссылка `current` переключается на неё. Предыдущие версии остаются на
сервере для быстрого отката.

## Файлы

- `server-setup.sh` — однократная базовая подготовка Ubuntu VPS;
- `nginx-site.conf.example` — HTTP-конфигурация Nginx до выпуска сертификата;
- `deploy.sh` — публикация, просмотр версий и откат;
- `check.sh` — локальная проверка шаблонов этой папки.

Все команды ниже предназначены для будущего Codex или администратора. Владелице
сайта не нужно самостоятельно вводить их в Терминале.

## Что нужно узнать перед началом

Пока неизвестны и намеренно не записаны в репозиторий:

- IP-адрес VPS;
- основной домен: с `www` или без `www`;
- публичный SSH-ключ Mac, с которого будет выполняться публикация;
- окончательный список 301-редиректов со старого сайта.

Не добавляйте в репозиторий пароли, приватные SSH-ключи или токены Beget.

## 1. Создание VPS

Для статического сайта достаточно начать с небольшого Ubuntu LTS VPS: один
процессор, 1 ГБ памяти и 10–20 ГБ диска. В Beget нужно добавить публичный
SSH-ключ и разрешить входящие соединения на порты 22, 80 и 443.

После получения IP будущий Codex должен сначала проверить SSH-доступ, не
отключая существующий способ входа.

## 2. Однократная подготовка сервера

Сначала скрипт копируется на VPS, затем запускается от `root`. Значение
`DEPLOY_PUBLIC_KEY` — публичная часть ключа, например строка, начинающаяся с
`ssh-ed25519`. Это не приватный ключ.

```bash
scp deploy/server-setup.sh root@VPS_IP:/root/nailsprofi-server-setup.sh
ssh root@VPS_IP
DEPLOY_PUBLIC_KEY='ssh-ed25519 ЗДЕСЬ_ПУБЛИЧНЫЙ_КЛЮЧ' \
  bash /root/nailsprofi-server-setup.sh
```

Скрипт:

- устанавливает Nginx, rsync, curl, UFW и Certbot;
- создаёт пользователя `deploy` без прав администратора;
- разрешает ему вход только по добавленному SSH-ключу;
- создаёт `/var/www/nailsprofi/releases`;
- открывает в UFW только SSH, HTTP и HTTPS;
- запускает Nginx.

Скрипт специально не отключает вход `root` и парольную авторизацию. Сначала
нужно открыть второе соединение и убедиться, что `ssh deploy@VPS_IP` работает.
Только затем можно отдельно усиливать SSH-настройки, предварительно проверив
`sshd -t`, чтобы не потерять доступ к серверу.

## 3. Установка конфигурации Nginx

В копии шаблона нужно заменить `__DOMAIN__` на реальный домен. Путь сайта уже
совпадает с `server-setup.sh`.

```bash
sed 's/__DOMAIN__/example.ru/g' \
  deploy/nginx-site.conf.example > /tmp/nailsprofi.conf
scp /tmp/nailsprofi.conf root@VPS_IP:/etc/nginx/sites-available/nailsprofi
ssh root@VPS_IP \
  'ln -sfn /etc/nginx/sites-available/nailsprofi /etc/nginx/sites-enabled/nailsprofi && nginx -t && systemctl reload nginx'
```

Перед включением конфигурации нужно проверить, не обслуживает ли стандартный
сайт Nginx тот же адрес. Не удаляйте существующие конфигурации вслепую.

Правило маршрутизации в шаблоне:

```nginx
try_files $uri $uri/ =404;
```

Сайт не является SPA, поэтому неизвестный URL должен возвращать `404`, а не
главную страницу.

## 4. Первая публикация

Публикация запускается на Mac из корня репозитория:

```bash
DEPLOY_HOST=VPS_IP \
SITE_URL=http://example.ru \
./deploy/deploy.sh publish
```

Можно не указывать `SITE_URL`, пока DNS ещё не переключён. В таком случае
скрипт проверит наличие `index.html` на VPS, но пропустит внешнюю HTTP-проверку.

`deploy.sh` перед загрузкой требует:

- чистое состояние Git без незакоммиченных файлов;
- ветку `main`;
- совпадение локального commit с актуальным `origin/main`;
- успешный `bun install --frozen-lockfile` и `bun run check`.

При загрузке права каталогов приводятся к `755`, а файлов — к `644`. Это важно:
локальные права некоторых изображений на Mac могут быть строже и не должны
делать их недоступными Nginx.

Если внешняя проверка новой версии не проходит, скрипт автоматически возвращает
предыдущую активную версию.

## 5. DNS и HTTPS

После успешной проверки VPS:

1. Направить A-записи основного домена и `www` на IPv4 VPS.
2. Не добавлять AAAA-запись, пока IPv6 действительно не настроен.
3. Дождаться обновления DNS.
4. Выпустить сертификат сразу для обоих имён:

```bash
ssh root@VPS_IP
certbot --nginx -d example.ru -d www.example.ru --redirect
certbot renew --dry-run
```

После выпуска сертификата нужно выбрать один основной адрес и настроить 301 с
другого (`www` -> без `www` либо наоборот). Выбор нельзя делать до того, как
владелец подтвердит реальный основной домен. HSTS следует включать только после
успешной проверки HTTPS и продления сертификата.

При переносе действующего сайта старый сервер лучше оставить включённым на
48–72 часа. Редиректы старых страниц на новые настраиваются отдельно; шаблон
не делает неизвестные перенаправления автоматически.

## 6. Последующие обновления

Обычный пользовательский процесс:

1. Попросить Codex изменить сайт, но не публиковать.
2. Проверить локальную desktop- и mobile-версию.
3. Явно разрешить commit и push.
4. Написать: «Я всё проверила. Опубликуй сайт».

Codex после разрешения запускает ту же команду `deploy.sh publish`, проверяет
главную страницу, `/services/` и корректный ответ `404`, затем сообщает домен и
опубликованный commit.

Публикация не запускается автоматически после каждого push.

## Просмотр версий и откат

```bash
DEPLOY_HOST=VPS_IP ./deploy/deploy.sh list

DEPLOY_HOST=VPS_IP \
SITE_URL=https://example.ru \
./deploy/deploy.sh rollback 20260808120000-1a2b3c4d5e6f
```

Имя версии нужно брать из команды `list`, не вводить наугад. Старые версии
пока не удаляются автоматически. Очистку стоит добавлять только когда каталог
`releases` действительно начнёт занимать заметное место.

## Проверка шаблонов

```bash
./deploy/check.sh
```

Перед реальным запуском будущий Codex обязан ещё раз прочитать этот README,
проверить актуальные рекомендации Beget, текущие DNS-записи, состояние Git и
содержимое всех команд с реальными значениями. Публикация, изменение домена,
DNS, Nginx или SSH выполняются только после явного подтверждения владельца.
